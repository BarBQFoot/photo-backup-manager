# ข้อกำหนดและแผนลงมือพัฒนา: Final Project Photo Backup

> ฉบับ 1.0 | อ้างอิงภาพโจทย์ Final Project และไฟล์ `ข้อสอบปฏิอบัติ Go.md` ที่ได้รับ  
> ใช้คู่กับ `แผนโครงงาน Final Project โปรแกรมสำรองรูปภาพจาก Flash Drive หรือโทรศัพท์มือถือ.md` ซึ่งเป็นภาพรวมของโครงงาน

> **Architecture Revision:** ไฟล์ภาพจริงต้องอยู่บน Drive/Filesystem ปลายทาง SQLite/GORM เก็บเฉพาะ Metadata ที่จับคู่ด้วย Path ในเวอร์ชันแรก, AI Description และ Backup History ห้ามเก็บ Image Binary/Base64/BLOB/Thumbnail Binary คำว่า “ข้อมูลรูป” ในเอกสารเดิมหมายถึง Metadata เท่านั้น ใช้ Specs ปัจจุบันใน `00-PROJECT-BLUEPRINT.md`, `01-API-CONTRACT.md`, `02-DATABASE-SPEC.md`, `03-UI-SPEC.md`, `05-UI-DESIGN.md` และ `04-FLOW-SPEC.md` เป็น Architecture ของรอบส่งงาน

> **ขอบเขตลดรูปที่ทีมเลือกสำหรับการส่งงาน:** เลือก Description-only: AI สร้างคำอธิบาย, ผู้ใช้ค้นด้วยช่องข้อความที่แก้ไขได้ และผลลัพธ์แสดงรูปจริงหลายรูปจาก Drive ไม่มี Tag/Tag Cloud/Category, Hash Identity, Rename/Changed Detection, Analysis Cache/Re-analysis อัตโนมัติ, Thumbnail Cache หรือ Metadata Portability ในรอบนี้ ส่วนด้านล่างที่อธิบายทางเลือกอื่นเป็น Requirement/ทางเลือกที่โจทย์เปิดไว้ ไม่ใช่ Feature ที่ทีมเลือกทำ

> **ลำดับอ้างอิง:** รายการที่เลือกทำและสัญญาระบบใน `00-PROJECT-BLUEPRINT.md`, `01-API-CONTRACT.md`, `02-DATABASE-SPEC.md`, `03-UI-SPEC.md`, `04-FLOW-SPEC.md` และ `05-UI-DESIGN.md` มีผลเหนือ checklist/ตัวอย่างทางเลือกที่ยังหลงเหลือในเอกสารฉบับยาวนี้ หากเนื้อหาขัดกัน ให้ยึดขอบเขต Description-only และ API/DB/UI/Flow Specs ปัจจุบัน

## อ่านส่วนนี้ก่อน

**แกนของ Final:** ทำโปรแกรมเดสก์ท็อปด้วย Wails + Nuxt + Go + SQLite/GORM ที่ย้ายรูปภาพได้ตามข้อสอบกลางภาค แล้วเพิ่มการวิเคราะห์และค้นหารูปหลายรูปด้วย Description เท่านั้น

**สิ่งที่ทราบแน่จากกลางภาค:** `/move` คือ **ย้ายไฟล์** และต้องลบต้นทางเมื่อสำเร็จ ไม่ใช่คัดลอกเก็บไว้ทั้งสองแห่ง หากย้ายข้ามไดรฟ์ไม่ได้โดยตรง ต้องคัดลอกให้ครบก่อนลบต้นทาง; ห้ามย้ายชื่อไฟล์ที่ซ้ำในปลายทางหรือฐานข้อมูล; ต้องบันทึกผ่าน GORM; แสดงเวลารวม; แสดงประวัติแยกตามปลายทาง; ตรวจไฟล์ที่หาย; ลบไฟล์แล้วอัปเดตฐานข้อมูล

**ขอบเขตที่ยังต้องยืนยัน:** Final เรียกโปรแกรมว่า Backup รูปภาพ และกล่าวว่า “ความสามารถของการ Backup เทียบเท่ากับข้อสอบกลางภาค” เอกสารนี้จึงถือพฤติกรรม **Move** เป็นเกณฑ์ทดสอบตั้งต้น แต่ควรถามอาจารย์ว่าต้องลบต้นทางจริงเหมือนกลางภาคหรืออนุญาตโหมด Copy เพิ่มหรือไม่ ห้ามเปลี่ยนเป็น Copy อย่างเดียวโดยไม่ได้ตรวจเกณฑ์

## 1. ตารางเทียบงานกลางภาคกับ Final

| ข้อจากกลางภาค | สิ่งที่ระบบต้องทำ | หน้าจอ/การกระทำใน Final | ตรวจรับอย่างไร |
| --- | --- | --- | --- |
| `/source <path>` | เลือกและจำต้นทาง | ปุ่มเลือกโฟลเดอร์/ไดรฟ์ต้นทาง | แสดงพาธและรายการไฟล์จริง |
| `/dest <path>` | เลือกปลายทาง เปิด/เตรียม DB ด้วย GORM และสแกนไฟล์หาย | ปุ่มเลือกปลายทาง + สถานะตรวจสอบ | เลือกปลายทางแล้วแสดงผล Integrity Scan |
| `/list source` | แสดงไฟล์ต้นทาง | ตารางไฟล์ก่อนย้าย | รายชื่อและจำนวนตรงกับโฟลเดอร์ |
| `/list dest` | แสดงไฟล์จริงที่ปลายทาง | คลังไฟล์ปลายทาง | เห็นไฟล์จริง ไม่ใช้ DB แทนรายการไฟล์ |
| `/list db [path]` | ดูประวัติของปลายทางที่กำหนดเท่านั้น; ถ้าไม่กำหนดปลายทางต้องแจ้งเตือน | แท็บประวัติ + ตัวเลือกปลายทาง | ไม่รวมข้อมูลจากปลายทางอื่น; กดก่อนเลือกปลายทางไม่ crash |
| `/move <files>` | ย้ายไฟล์ที่เลือก | เลือกหลายไฟล์แล้วกด “ย้ายไปปลายทาง” | ย้ายเฉพาะที่เลือก; ลง DB หลังสำเร็จ |
| `/move all` | ย้ายทุกไฟล์ พร้อมข้ามชื่อซ้ำ | ปุ่ม “ย้ายทั้งหมด” | ต้นทางหายเฉพาะไฟล์ที่สำเร็จ; แสดงจำนวนย้าย/ข้าม/ผิดพลาด |
| ย้ายข้ามไดรฟ์ | ลอง move แล้ว fallback เป็น copy ให้เสร็จ + delete | ทำงานหลังปุ่มย้าย | ทดสอบกับ USB จริง; หาก copy ล้มเหลวต้นทางต้องอยู่ |
| Duplicate Protection | เช็กชื่อในโฟลเดอร์ปลายทาง **และ** DB; ห้ามเขียนทับ | แจ้งเตือนข้างชื่อไฟล์และในสรุป | ชื่อซ้ำไม่ถูกย้าย, ไม่เขียนทับ, ไม่ลง record ซ้ำ |
| เวลาประมวลผล | วัดตั้งแต่เริ่มย้ายจนจบทุกไฟล์ | สรุปเวลารวมเป็น ms/s | เวลาแสดงจากการทำงานจริง |
| `/check` | เทียบ record ของปลายทางกับไฟล์จริง; รายงาน Missing Files | ปุ่ม “ตรวจสอบไฟล์” | ลบไฟล์ทดสอบจากปลายทางแล้วพบชื่อที่หาย |
| `/delete ...` | ลบไฟล์จริงในโฟลเดอร์เป้าหมายและอัปเดต DB | ปุ่มลบพร้อมระบุขอบเขตอย่างชัด | ไฟล์ถูกลบและสถานะฐานข้อมูลถูกปรับ |
| `/exit` | ออกโดยไม่ค้าง process/DB | ปิดหน้าต่างแอป | เปิดใหม่ได้ ประวัติยังอยู่ |
| ภาพ Final: วิเคราะห์รูป | ทำคำอธิบายภาพหรือแท็กอย่างน้อยหนึ่งอย่าง | หน้ารายละเอียด/งานวิเคราะห์ | รูปหลายรูปมีข้อมูลวิเคราะห์ให้ค้น |
| ภาพ Final: ค้นรูป | ทีมเลือกค้น Description เท่านั้น; ผลเป็นภาพหลายรูป | ช่องค้นใน Gallery จำกัดตาม Destination | คืนรูปครบทุกผลที่ตรงและแสดงภาพได้ |

**หมายเหตุเรื่องประสิทธิภาพ:** เกณฑ์กลางภาคมีการเทียบความเร็วกับโปรแกรมตัวอย่าง 1.5 เท่า แต่ไม่ทราบสภาพแวดล้อมหรือไฟล์ตัวอย่างของ Final จึงควรวัดเวลาและลดงานซ้ำจริง โดยไม่ใส่ตัวเลขรับประกันที่พิสูจน์ไม่ได้

## 2. ข้อกำหนดเชิงพฤติกรรมที่ใช้สร้างโปรแกรม

### 2.1 ตั้งค่าต้นทางและปลายทาง

- ผู้ใช้เลือกต้นทางและปลายทางผ่านหน้าจอ Wails; Go ตรวจว่าพาธมีอยู่และเข้าถึงได้
- ตรวจปลายทางไม่ใช่ต้นทาง และไม่อยู่ภายในต้นทาง เพื่อไม่สแกนไฟล์ที่กำลังสร้างซ้ำ
- บันทึกพาธและแสดงรายการต้นทาง ปลายทาง และประวัติฐานข้อมูล **แยกกัน**
- ถ้าเปิดประวัติก่อนกำหนดปลายทาง ให้แจ้ง “กรุณาเลือกโฟลเดอร์ปลายทาง” และไม่เกิดข้อผิดพลาดที่ทำให้โปรแกรมปิด
- เมื่อเปลี่ยนปลายทาง ต้องโหลดประวัติของปลายทางใหม่และสแกนรายการ Missing ใหม่

### 2.2 ย้ายไฟล์

1. รับไฟล์ที่เลือกหรือทั้งหมดจากต้นทาง และบันทึกเวลาเริ่ม
2. ก่อนแต่ละไฟล์ ตรวจว่า **ชื่อไฟล์** มีในปลายทางหรือใน record ของปลายทางนั้นหรือไม่ หากมีให้ข้ามและแจ้งเหตุผล; ไม่เขียนทับ
3. พยายามย้ายไฟล์ในระบบไฟล์ก่อน หากเกิดข้อผิดพลาดจากการย้ายข้ามไดรฟ์ ให้คัดลอกไปไฟล์ชั่วคราวที่ปลายทาง ตรวจว่าคัดลอกสมบูรณ์ แล้วจึงเปลี่ยนเป็นชื่อจริงและลบต้นทาง
4. เมื่อไฟล์ปลายทางพร้อมและลบต้นทางตามนโยบายแล้ว จึงบันทึก record ผ่าน GORM; หาก DB บันทึกล้มเหลว ต้องแจ้งสถานะไม่ตรงกันและเตรียมทางกู้คืน/ตรวจซ้ำ
5. ส่งความคืบหน้าแต่ละไฟล์และสรุปจำนวนสำเร็จ ข้าม ล้มเหลว พร้อมเวลารวม

**ความปลอดภัยของข้อมูล:** อย่าลบต้นทางเมื่อคัดลอกไม่ครบหรือมีข้อผิดพลาด; อย่าเขียนทับไฟล์ปลายทางเงียบ ๆ; อย่าสรุปว่าไฟล์สำเร็จหากฐานข้อมูลยังบันทึกไม่สำเร็จ กรณีปิดแอประหว่างทำงานต้องแจ้งผลของไฟล์ที่ทำได้แล้วเมื่อเปิดครั้งถัดไป

### 2.3 ลบและตรวจความถูกต้อง

- ฟังก์ชันตรวจเทียบเฉพาะ record ที่ยังถือว่าอยู่ในปลายทางปัจจุบันกับไฟล์จริง หากไม่มีไฟล์ให้รายงานชื่อและพาธเป็น `missing`
- ตรวจเมื่อเลือกปลายทางและเมื่อผู้ใช้กดตรวจเอง
- ลบไฟล์จริงก่อน แล้วอัปเดตสถานะใน DB ผ่าน GORM; ถ้าลบไม่สำเร็จอย่าระบุใน DB ว่าลบแล้ว
- **ความกำกวมในไฟล์กลางภาค:** ตารางคำสั่งเขียน `/delete <file1>, ...` หรือ `all` แต่ rubric ทดลอง `/delete dest <filename>`; สเปก UI ควรแสดงชัดว่า “ลบจากปลายทาง” และถามอาจารย์หากต้องรองรับการลบจากต้นทางด้วย
- แยกสถานะ `deleted` (ลบผ่านแอป) กับ `missing` (ไฟล์หายไปเอง) เพื่อไม่ให้รายงานลบโดยตั้งใจเป็นความผิดปกติ

## 3. งานวิเคราะห์รูปและการค้นหาของ Final


## 3.1 แนวทาง AI ที่กำหนดสำหรับ Final

สำหรับส่วนการวิเคราะห์ภาพ ให้ใช้ **Google Gemini API** เป็นบริการ AI ออนไลน์ โดยกำหนด **Gemini 2.5 Flash** เป็นโมเดลหลักสำหรับการวิเคราะห์ภาพ

### วัตถุประสงค์

เมื่อระบบพบไฟล์ภาพที่ผู้ใช้เลือก ระบบสามารถส่งภาพไปยัง Gemini เพื่อวิเคราะห์เนื้อหาภายในภาพ แล้วนำผลลัพธ์กลับมาเก็บเป็น Metadata ของไฟล์

รุ่นส่งงานนี้เลือกเฉพาะ **Description** — คำอธิบายภาพแบบสั้นและเข้าใจง่าย ไม่มี Tags หรือ Category

ตัวอย่าง:

```json
{"description": "ภาพแมวกำลังนอนอยู่บนโซฟาในบ้าน"}
```

### ลำดับการทำงาน

```text
เลือกภาพ
   ↓
ตรวจสอบว่ามีผลวิเคราะห์เดิมหรือไม่
   ↓
ส่งภาพที่ผู้ใช้เลือกไป Google Gemini API
   ↓
Gemini 2.5 Flash วิเคราะห์ภาพ
   ↓
รับ Description
   ↓
ตรวจสอบและแปลงผลลัพธ์
   ↓
บันทึกลง SQLite
```

### ข้อกำหนดของ AI

- เก็บ Description แยกจากข้อมูลไฟล์พื้นฐาน
- หาก API ล้มเหลว ไฟล์ต้นฉบับต้องไม่ถูกแก้ไขหรือลบ
- ต้องแสดงสถานะให้ผู้ใช้ทราบ เช่น `กำลังวิเคราะห์`, `สำเร็จ`, `ล้มเหลว`
- API Key ต้องไม่ hard-code ลงใน Source Code
- ต้องรองรับกรณีไม่มี Internet และ API Error
- ควรจำกัดขนาด/ชนิดไฟล์ก่อนส่งไป API

### AI Metadata ที่ควรเก็บ

```text
description
ai_status
```

ตัวอย่าง:

```text
description: ภาพแมวกำลังนอนอยู่บนโซฟา
ai_status: analyzed
```

### Description Search ใน Gallery

Search เป็นความสามารถที่ต้องทำในรุ่นส่งงาน โดยอยู่ในหน้า Gallery และค้นเฉพาะ Description ของ Destination ที่เลือก ผู้ใช้พิมพ์/แก้คำค้นและเห็นภาพจริงที่ตรงกันหลายภาพ ไม่ทำ Tag Cloud หรือ Advanced Search

### การเลือกโมเดล

กำหนดให้ `gemini-2.5-flash` เป็นโมเดลหลักในเอกสารและโค้ดที่พัฒนา

หากในอนาคต Google มีโมเดล Flash รุ่นใหม่ที่เหมาะสมกว่า สามารถเปลี่ยน Model ID ได้โดยไม่เปลี่ยนโครงสร้างข้อมูลหรือ Workflow หลักของระบบ

ไม่ควรผูกระบบกับโมเดลสร้างภาพ เช่น `gemini-2.5-flash-image` หากจุดประสงค์ของฟีเจอร์นี้คือ **วิเคราะห์ภาพเพื่อสร้าง Metadata** ไม่ใช่สร้างภาพใหม่

| Tag | วิเคราะห์ภาพแล้วเก็บแท็ก | **Tag Cloud** ของแท็กที่มีจริง | กดแท็กแล้วแสดงภาพทุกภาพที่มีแท็ก |
| ทั้งสองอย่าง | เก็บคำอธิบายและแท็ก | มีทั้งช่องค้นและ Tag Cloud | ค้นคืนตามทั้งสองวิธี |

สำหรับแนวทางที่ทีมเลือก ให้ใช้ Gemini API วิเคราะห์ภาพเมื่อผู้ใช้สั่งเอง; แสดงผล Description จริงและข้อผิดพลาดจริง ไม่สร้างผลจำลองเป็นผลวิเคราะห์

**ขั้นต่ำสำหรับผลค้นหา:** ค้นคำไทยได้, ค้นแล้วได้หลายรูป, เปิดรูปดูได้, ไม่พบผลมีข้อความอธิบาย, ไฟล์ถูกลบหรือหายไม่แสดงเป็นรูปที่เปิดได้โดยไม่มีคำเตือน

## 3.4 Gemini API Key และการตั้งค่า Google AI

โปรเจกต์ใช้ **Google Gemini API** สำหรับการวิเคราะห์ภาพ ดังนั้นต้องสร้าง API Key สำหรับ Gemini API แล้วนำ Key มาใช้กับระบบ

ข้อมูลที่ต้องมีสำหรับการตั้งค่า:

```text
API Provider:
Google Gemini API

Model:
gemini-2.5-flash

Authentication:
API Key

Environment Variable:
GEMINI_API_KEY
```

### การตั้งค่า API Key

1. สร้าง API Key สำหรับ Gemini API ใน Google AI Studio
2. คัดลอก API Key มาเก็บไว้ใน Environment Variable ของเครื่องที่ใช้พัฒนา
3. ระบบอ่านค่าจาก `GEMINI_API_KEY`
4. ห้ามเขียน API Key ลงใน Source Code โดยตรง
5. ห้าม Commit API Key ลง Git / GitHub
6. หาก API Key ถูกเปิดเผย ต้องยกเลิก (Delete / Revoke) Key เดิมและสร้าง Key ใหม่

ตัวอย่าง:

```text
GEMINI_API_KEY=<YOUR_GEMINI_API_KEY>
```

**หมายเหตุด้านความปลอดภัย:** API Key ที่ปรากฏในภาพหรือข้อความสำหรับการตั้งค่าโปรเจกต์ไม่ควรนำมาใส่ไว้ในเอกสาร, Source Code หรือ Repository แบบเป็นค่าจริง ให้ใช้ `<YOUR_GEMINI_API_KEY>` แทนเสมอ

### ข้อมูลจาก Google AI Studio

หน้าจอ API Key จะแสดงข้อมูล เช่น:

- API Key
- Key Name
- Google Cloud Project Name
- Project Number

สำหรับระบบ แอปจำเป็นต้องใช้ **API Key** เป็นหลัก ส่วน Project Name และ Project Number ใช้สำหรับระบุ/ตรวจสอบโปรเจกต์ของ Google และไม่จำเป็นต้อง hard-code ลงในแอป

### การตรวจสอบก่อนใช้งาน

- [ ] มี Gemini API Key
- [ ] ตั้งค่า `GEMINI_API_KEY` สำเร็จ
- [ ] แอปสามารถอ่าน Environment Variable ได้
- [ ] ใช้ Model `gemini-2.5-flash`
- [ ] ไม่พบ API Key จริงใน Source Code
- [ ] ไม่พบ API Key จริงใน Git Repository
- [ ] ทดสอบส่งภาพตัวอย่างและรับผล Description ได้


## 4. แบบข้อมูลที่แนะนำ

| Model | ฟิลด์สำคัญ | หมายเหตุ |
| --- | --- | --- |
| `BackupJob` | ID, Source, Destination, StartedAt, CompletedAt, TotalFiles, SuccessCount, FailedCount, Status | ประวัติการสำรองหนึ่งครั้ง; รายละเอียด canonical อยู่ใน `02-DATABASE-SPEC.md` |
| `FileRecord` | ID, FileName, FullPath, SizeBytes, MimeType, ModifiedAt, BackupJobID, AIStatus, Description, Status | Metadata เท่านั้น; ไม่มี Image Binary, Hash, Category หรือ Tag |

**ข้อกำหนด DB:** การสร้างตารางและ CRUD ใช้ GORM; Query ประวัติและ Search ต้องจำกัด Destination; ใช้ Full Path จับคู่ในรุ่นแรก; ห้ามเก็บรูปจริง/Base64/BLOB/Thumbnail Binary

**Integrity ตามโจทย์กลางภาค:** ตรวจ record ที่มีแต่ไฟล์จริงหายจากการมีอยู่ของไฟล์; ไม่เพิ่ม Hash Identity ในรุ่นส่งงาน

## 5. หน้าจอขั้นต่ำ

1. **Move Photos:** เลือกต้นทางและปลายทาง แสดงจำนวนรูป รายการที่เลือกได้ กล่องยืนยัน และ Progress; ไม่แยก Dashboard เพิ่ม
2. **รายการต้นทาง:** ไฟล์จริง เลือกบางไฟล์หรือทั้งหมด และเริ่มย้าย
3. **สถานะงาน:** progress รายไฟล์ ผลข้ามชื่อซ้ำ ข้อผิดพลาด และเวลารวม
4. **คลังภาพ / Gallery:** แสดงรูปจริงและ Description พร้อม Analyze; ช่องค้น Description อยู่ใน Gallery และจำกัดตาม Destination

**การเชื่อมหน้าจอ:** Nuxt รับข้อมูลจาก Go ผ่าน Wails binding; การสแกน ย้าย ลบ และ query DB ทำใน Go; ความคืบหน้าส่งกลับ UI เป็น event หรือกลไกที่ Wails รองรับ อย่าให้การย้ายไฟล์ใหญ่ทำให้หน้าจอค้าง

## 7. ชุดทดสอบสาธิตที่ควรเตรียม

- เปิดแอปใหม่ → กดดูประวัติ DB ก่อนเลือกปลายทาง → เห็นข้อความแจ้ง ไม่ crash
- ตั้ง Source จาก USB และ Destination ในคอม → เห็นไฟล์ต้นทางและสแกน Missing
- ย้ายบางไฟล์ แล้วใช้ “ย้ายทั้งหมด” กับไฟล์ที่เหลือ → แสดงเวลาและ record ของปลายทางนั้น
- สร้างไฟล์ชื่อเดิมที่ต้นทาง → สั่งย้าย → ข้ามชื่อซ้ำพร้อมคำเตือน ไม่เขียนทับ
- เพิ่มปลายทางที่สอง → ประวัติแยกกัน ไม่รวมข้อมูลจากปลายทางแรก
- ลบไฟล์ในปลายทางด้วย File Explorer/Finder → กดตรวจ → รายงานชื่อ Missing
- ลบไฟล์ผ่านแอป → ไฟล์หายจริงและ DB ปรับสถานะ โดยไม่ปนกับ Missing
- วิเคราะห์รูปอย่างน้อยสองรูปให้ตรงคำค้น/แท็กเดียวกัน → ค้นแล้วได้ผลหลายรูป; เปลี่ยนคำค้นหรือกดแท็กอื่นได้
- ปิดและเปิดใหม่ → ประวัติและข้อมูลวิเคราะห์ยังอยู่

## 9. นิยามว่าเสร็จ

แอปที่ build แล้วบน Windows และ macOS เลือกพาธได้ แสดง Source/Dest/DB ตามปลายทาง ย้ายไฟล์ข้ามไดรฟ์โดยไม่ทำต้นฉบับสูญหายเมื่อย้ายล้มเหลว ข้ามชื่อซ้ำพร้อมแจ้งเตือน บันทึกผ่าน GORM แสดงเวลารวม ตรวจ Missing และลบอย่างสัมพันธ์กับ DB ได้ อีกทั้งวิเคราะห์รูปอย่างน้อยหนึ่งวิธีและค้นคืนเป็นรูปหลายรูปผ่านหน้าจอตามเงื่อนไข Final
