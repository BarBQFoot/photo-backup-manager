# อ่านภาพและแปลคำบรรยายพร้อมกัน

ปรับวันที่ 24 ตุลาคม 2026: Florence ใช้ beams=1, รองรับชุดละ 1/2/4 รูปและเลือกขนาดตามโปรไฟล์ความเร็วของ GPU สำหรับงานตั้งแต่ 100 รูป ส่งคำบรรยายอังกฤษทุก 100 รายการให้เธรดแปล ขณะที่เธรดหลักอ่านรูปถัดไป รักษาคำขอ Gemini ทีละหนึ่งคำขอและช่วงห่าง 10 วินาทีตามเดิม รูปที่ทำสำเร็จเก็บแคชและบันทึกด้วย file_id ที่ตรวจแล้ว

## ผลวัดบนเครื่อง Windows / CUDA

Florence-2-base-ft, PyTorch 2.13.0+cu126, float16 รูปเดียวกัน 12 รูป โหลดโมเดลครั้งเดียว warmup แต่ละตัวเลือกและวัดซ้ำ 3 ครั้ง ตารางเป็นค่ามัธยฐาน ไม่รวมโหลดโมเดล/นำเข้า dependencies/แปลไทย/ฐานข้อมูล/หน้าจอ

| beams | รูปต่อชุด | เวลา 12 รูป | เฉลี่ยต่อรูป | CUDA tensor peak |
| --- | --- | --- | --- | --- |
| 3 | 1 | 4.093 วินาที | 0.3411 วินาที | 627.5 MB |
| 1 | 1 | 3.966 วินาที | 0.3305 วินาที | 627.5 MB |

ผลนี้ประมาณ 2 เท่าเฉพาะขั้นอ่านภาพหลัง warmup ไม่ใช่ผลเวลา 1000 รูปจนได้ภาษาไทย และยังไม่ได้วัดจริงบน Mac/MPS คำบรรยายของ beams=1 ต่างจาก beams=3 จึงต้องตรวจคุณภาพกับภาพจริง ไม่ได้มีผลประเมินความแม่นยำ

รายงานพร้อมคำบรรยายแต่ละรูป: `results/performance/florence_20261024_154422.json` สคริปต์ `tools/benchmark_caption_speed.py` ใช้เทียบซ้ำกับชุดอื่นได้

ทดสอบ Python 39 รายการ รวมการซ้อนงานอ่าน/แปลด้วย synchronization events, คำตอบกลับมาสลับลำดับ, timeout แล้วทำต่อ, รูปเสีย, OOM ลดขนาดชุด, การเลือก/ใช้ซ้ำโปรไฟล์ และการตัด padding หลัง EOS ผ่าน เทสต์ Go ทั้งหมดผ่านเมื่อรันใน environment ที่อนุญาตไฟล์ชั่วคราวและ HTTP จำลอง ไม่ได้เรียก Gemini จริงในการทดสอบ

## ลองรอบจริง

ปิดแอปเดิมแล้วเปิด EXE ใหม่ หรือเริ่ม `wails dev` ใหม่ เลือกวิเคราะห์รูป 100 รูปใหม่หรือสั่งวิเคราะห์ซ้ำ รูปที่มีคำบรรยายอยู่แล้วไม่ถูกเปลี่ยนอัตโนมัติ ไม่จำเป็นต้องลบรูป ฐานข้อมูล แคช หรือโมเดลเพื่อเปิดใช้โค้ดใหม่

หน้าจอแสดงตัวนับอ่านภาพและคำบรรยายไทยพร้อมกัน โปรไฟล์ครั้งแรกมีเวลาเทียบชุดเพิ่ม และเปิดรอบถัดไปจะใช้โปรไฟล์เดิม รายงาน `pipeline_summary.json` ในแคช `ai/captions` แสดงเวลาของงานล่าสุด เวลาย่อยอ่านและแปลซ้อนกันจึงห้ามบวกเป็นเวลารวม

## รุ่นเก็บโมเดลไว้ระหว่างงานและรวมสถานะ DB

ก่อนเริ่มงาน ใช้ธุรกรรมเดียวเปลี่ยนเฉพาะ `ai_status` ของไฟล์ active โดยแบ่ง SQL เป็นไม่เกิน 500 ID ต่อคำสั่ง ไม่เขียนทับคำบรรยายผู้ใช้และไม่เปลี่ยนสถานะไฟล์ missing/deleted หากคำสั่งใดล้มเหลวจะ rollback ทั้งการเลือก ผลคำบรรยายที่กลับมายังคงตรวจและบันทึกทีละรูปทันทีเหมือนเดิม

ผล benchmark SQLite แยก 1000 แถวบนเครื่อง Windows: แบบเขียนทีละรูป 1.005 วินาที เทียบกับธุรกรรมรวม 0.0064 วินาที นี่เป็นผลเฉพาะการตั้งสถานะก่อนงาน จึงใช้สรุปว่าส่วนต่าง 76 วินาทีของรอบ 5:30 เป็น DB ทั้งหมดไม่ได้

Python ใช้ JSON หนึ่งคำขอต่อบรรทัดและเก็บ Florence เดิมไว้ใน worker ระหว่างที่แอปเปิด งานถัดไปใช้โมเดลเดิมจนกว่าจะปิดแอป เปลี่ยน environment/runtime หรือ worker ล้ม งานที่ล้มจะไม่ส่ง API ซ้ำโดยอัตโนมัติ ระหว่างแอปเปิด โมเดลจะใช้ RAM/VRAM ค้างไว้ เมื่อปิดแอปหรือยกเลิกงานจะหยุด worker รวมถึง Python child ของ venv บน Windows งานใหม่หลัง worker ล้มเริ่มโปรเซสใหม่และใช้แคชผลสำเร็จได้

ทดสอบ Florence จริงผ่าน Go bridge ด้วยภาพที่ไม่เคยอยู่ในแคชของการทดสอบ 2 รูป: งานแรก 40.716 วินาที (โหลดโมเดล 36.043 วินาทีและ warmup ในภาพแรก) งานถัดไป 0.233 วินาที โดยใช้ PID เดิมและไม่มีการโหลดโมเดลใหม่ ปิดคีย์ Gemini ในการทดสอบ ไม่มีการแปลจริงหรือวัดเวลารวม 1000 รูป ผลอยู่ `results/performance/resident_worker_smoke.json` งานแรกหลังเปิดแอปยังมีค่าโหลดโมเดลตามปกติ

รายงาน Go เพิ่มที่ `analysis_summary.json` ใต้แคช `ai` แยกเวลาตรวจ/เตรียมข้อมูล ตั้งสถานะ เปิด worker ทำงานกับ worker และบันทึกผล พร้อม flag ว่าใช้ worker ซ้ำ เวลา Worker รวมการบันทึกผลที่รับมาด้วย จึงห้ามบวกทุกช่องเป็นเวลารวม หน้าจอแสดงเวลาจนรีเฟรชรายการเสร็จในข้อความผลวิเคราะห์

ทดสอบเพิ่ม: การใช้ Python เดิมหลายคำขอ, ระบาย error/done ก่อนรับงานใหม่, worker ล้มแล้วเริ่มใหม่, context ถูกยกเลิก, ปิดแอประหว่างทำงาน, bulk status ข้ามแถวที่ไม่ active และ rollback ข้ามหลาย SQL chunks ทั้งหมดผ่าน
